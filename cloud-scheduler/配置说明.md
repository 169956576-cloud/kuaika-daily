# Cloudflare 每半小时触发更新

当前状态：程序已准备，尚未连接 Cloudflare、尚未部署，GitHub 原有定时任务继续保留。

这里将定时触发交给 Cloudflare Workers，实际浏览器抓取、保存行情和 Pages 发布继续由 GitHub Actions 完成。两家云服务均可能延迟；这不是保证准点完成的实时系统。重新抓取成功不代表价格一定发生变化。

## 1. 先发布 GitHub 修改

在之前已登录 GitHub 的 PowerShell 运行项目里的 `发布到GitHub.ps1`，等待 Actions 完成。新流程会重试抓取 3 次，失败后保留旧快照、发布网站并把整个运行标为失败。

## 2. 创建账号和定时器

1. 打开 https://dash.cloudflare.com/sign-up 注册、验证邮箱并登录。无需添加域名。
2. 打开 Workers & Pages，创建 Worker，名称填 `kuaika-scheduler`。先用默认示例创建，进入编辑代码页面。
3. 用同目录 `worker.mjs` 的完整内容替换默认代码，保存并部署。此时不要添加定时触发器。

## 3. 仅授权 GitHub 工作流触发

1. 在已登录 GitHub 的浏览器打开 https://github.com/settings/personal-access-tokens/new ，创建 fine-grained token。
2. Resource owner 选 `169956576-cloud`；Repository access 选择 Only select repositories，仅选 `kuaika-daily`。
3. Repository permissions 仅将 Actions 设为 Read and write。Metadata 的默认只读保留。不需要源码写入权限。
4. 设置可管理的有效期；到期前需更换 Cloudflare 中的密钥，否则更新请求会失败。复制生成的值，不要发送到聊天、提交到仓库或写入网页源码。
5. Cloudflare Worker 的 Settings → Variables and Secrets 添加 Secret，名字必须是 `GITHUB_DISPATCH_TOKEN`，值填刚生成的 GitHub token，保存并部署。

## 4. 设置半小时触发并验证

1. Worker 的 Settings → Triggers / Cron Triggers 添加 `*/30 * * * *`。规则按 UTC 执行，对北京时间同样是每小时 00、30 分钟。Cloudflare 配置传播可能需要数分钟。
2. 在 Worker 的 Observability / Logs 查看调用记录。`accepted: true` 仅表示 GitHub 接受触发请求，不代表数据抓取或部署已经成功。
3. 在 https://github.com/169956576-cloud/kuaika-daily/actions 查看新运行，触发事件应为 `workflow_dispatch`。确认 Refresh daily source snapshot 和 Deploy site 成功。
4. 打开网站核对“来源快照”时间，并与上一次比对。观察至少两个连续时段的外部触发和部署，再删除 `.github/workflows/publish.yml` 的 `schedule` 段，保留 `push` 和 `workflow_dispatch`。不要在外部触发验证前删备用任务。

Cloudflare 日志和 GitHub Actions 是运行记录；当前没有配置邮件、短信等失败提醒。可在 GitHub 个人通知设置中启用 Actions 失败通知。日志保留和服务额度以账号后台为准。

## 费用和限制

- 计划每天触发 48 次，不调用 AI，不消耗 AI Token。
- GitHub token 是调用授权凭据，不是按字数收费的 AI token。
- Cloudflare 请求/日志、GitHub 运行和公开数据源访问受各自的套餐、配额及条款限制；没有自动开通付费套餐。不要将此说明视为任何用量下永久免费的保证。
- 公共请求只返回 404，不能通过访问 Worker URL 触发 GitHub 操作。
- 同步仅涵盖现有抓取器读取的卡战备配装与四类制造数据，没有新增子弹买卖行情来源。

## 命令行部署（可选）

如果使用本机 Wrangler，进入本目录依次运行：`npx wrangler@4 login`、`npx wrangler@4 deploy`、`npx wrangler@4 secret put GITHUB_DISPATCH_TOKEN`。最后一条交互式输入密钥。此路径在首次部署时即启用 cron，密钥尚未写入时可能产生失败日志；推荐新用户使用上面的后台流程，先写密钥再添加 cron。

本机验证：在项目目录运行 `node --test cloud-scheduler/scheduler.test.mjs`。
